# Pocket — application audit, 2026-10-25

## Context

Fourth audit round. Rounds one (#683/#685, Sept) and two (#786/#795) swept
security/infra, decimal-safety and concurrency. Round three
(`docs/audits/2026-10-12-app-audit.md`, HEAD `bc905ea6`) went deeper into shared-resource
mutation paths, the cash-boundary and transfer invariants, tax rules, rate-limit/resilience,
and a **live** browser walkthrough of every route at phone/tablet/desktop widths on the demo
seed. Round three produced 62 A–G findings plus 8 G proposals; **all 79 of its
`audit-2026-10` issues are closed**, and **154 commits** have landed since `bc905ea6`.

This round re-baselines the **whole web UI** against the current HEAD `149bceae` and splits
the work in two:

- a **regression check** of every round-three finding, so the next round starts from a known
  baseline instead of re-finding closed defects; and
- **new gaps**, concentrated in the surfaces that did not exist when round three ran — the
  in-app assistant, the command palette, the Indonesian final-tax module, the redesigned
  onboarding — plus a fresh accessibility and responsive sweep.

This file _is_ the report. Fixes are to be carried out by other models, so every finding has
an ID, a severity, a `file:line`, a concrete failure scenario, **one** preferred fix, and a
verification step. Findings are grouped into PR-sized batches.

**Evidence tags:** `[read]` = verified by reading the code at HEAD `149bceae`; `[live]` =
reproduced in the running app; `[sweep]` = reported by a static sweep and not independently
re-read (sweep line numbers may drift).

**IDs:** round-four findings are prefixed `R4-`. **Round-three IDs (`A1`, `D1`, `G5`…) are
unrelated to the `R4-` IDs below** — the two documents use the same letters.

**Headline:** one confirmed **blocker** — a failed load in the tax loss-carry-forward editor
leaves the fields at zero and the Save button live, so one click destroys a real carry-forward
— plus **17 major** findings led by a translation message that renders as a raw key on
Settings › Connections, an Activity ledger that silently ignores the holder scope, a
trade-log chart that draws a loss year as an upward bar, and charts with no accessible name
at all. The accessibility and responsive work that round three drove is genuinely in place:
skip link, single `h1`, bound form labels, a gain-figure basis, a `—` for at-cost holdings,
a 44 px touch-target floor, `prefers-reduced-motion` on every chart, and locale-aware numeric
input. What is left is mostly **new surfaces** that never went through that pass.

## Batch A — data loss & destructive actions (`fix(tax)`)

### R4-A1 · Fx1 · Blocker · `[read]` — a failed load in the loss-carry-forward editor wipes the tax loss pots on the next Save

- `apps/web/src/components/tax/loss-carryforward-editor.tsx:30-31` initialises both amount
  fields to the string `"0"`; `:45-47` swallows a failed load
  (`catch(() => { /* Silently ignore — fields keep their current values */ })`); `:59-60`
  submits `stock || "0"` / `general || "0"` unconditionally; `:139` renders
  `<Button onClick={handleSave} disabled={saving}>` — the only disabled state is "a save is in
  flight".
- Scenario: the user opens Settings › Tax, the carry-forward card mounts, and its
  `GET /tax/loss-carryforward` request fails for any transient reason (API restart, PGlite
  lock, a dropped connection). The card renders `0 / 0` with **no error, no loading state and
  no indication that anything failed**. The user presses Save once — and the server now holds
  `stock: 0, general: 0` for that year. The carry-forward is gone, and because it feeds the
  estimated tax, the allowance usage and the harvest suggestions, the tax figures silently
  change with no visible error anywhere.
- The defect is the combination of a silent `catch` and a destructive action that is enabled
  while the component does not know what it is editing. The _trigger_ is probabilistic; the
  _consequence_ is deterministic and irreversible.
- Fix: track a `loaded` state that is only set after a successful fetch; render the Save
  button disabled (and the fields read-only) until then; on failure render an inline error
  with a Retry **and keep Save disabled**. Never submit a value the user did not see loaded.
- Verify: stub the carry-forward request to fail, reload Settings › Tax, confirm the Save
  button is disabled and no error is swallowed; then confirm a successful load enables Save
  and that editing + saving persists the value.

## Batch B — forms & validation feedback (`fix(web)`)

### R4-B1 · Fx2 · Major · `[read]` — the transaction form throws away the API's field-level validation and shows one generic banner

- `services/api/src/routes/transactions/crud.ts:37,155` parse the payload with
  `transactionInputSchema`; `services/api/src/app.ts:217-218` turns a `ZodError` into
  `400 { error: "validation_error", issues: error.issues }` — a **field-pathed** list.
  `packages/api-client/src/index.ts:2317-2333` (`apiErrorCode`) extracts only the `error`
  string and drops `issues`. `apps/web/src/components/add-transaction-form/use-transaction-form.ts:456-457`
  then maps the result to a single banner: `code && t.has(\`loanErrors.${code}\`) ? … : t("error")`—`validation_error` is not a loan error, so **every** validation failure renders the same
  generic string.
- The form has no field-level error state at all: `NumberField`/`Input` take no `error` prop
  and no `aria-invalid` / `aria-describedby`, so the user is told "something went wrong" and
  must guess which of a dozen fields was wrong. A screen-reader user gets one alert and no
  association with the offending control.
- Scenario: the user enters a negative quantity, or omits a required field for the chosen
  type, and presses Save. The sheet bounces with a generic error and no field highlighted.
- Fix: add `apiErrorIssues(err)` to `@portfolio/api-client` (parse `err.body`, return
  `issues`), map each `issue.path` to a field key, and render it inline under the control with
  `aria-invalid` + `aria-describedby`; keep the banner for failures that are not field-bound.
- Verify: post an invalid transaction and confirm the offending field shows the API's message
  and is reachable by keyboard; confirm `aria-invalid` is set.

### R4-B2 · Fx3 · Major · `[read]` — the add-transaction totals ignore the app locale while the inputs above them don't

- `apps/web/src/components/add-transaction-form/totals.ts:81-89` exports a **second** money
  formatter that shadows the canonical one in `lib/utils.ts`:
  `n.toLocaleString("en-US", …)` with the raw ISO code as a prefix (`"EUR 1,234.50"`).
  It is used by `summary-rail.tsx:71,79,87,97` and `pricing-fields.tsx:144`.
- The number inputs in the same sheet are locale-aware: `number-format.ts:67`
  `formatGrouped(raw, locale)` renders `"1.234,56"` in `id`/`de`.
- So in one sheet the user sees the amount they typed as `1.234,56` and the total next to it
  as `EUR 1,234.56`, while the rest of the app (and the canonical `formatMoney`) renders
  `€1.234.567,50`. `Intl.NumberFormat("en", {style:"currency",currency:"EUR"})` → `€1,234,567.50`;
  `Intl.NumberFormat("id", …)` → `€1.234.567,50` — the shadowing helper produces a third
  spelling.
- Round three's E2 fixed the _input_ path and left this sibling; it is the same defect class
  one file over.
- Fix: delete `totals.ts`'s `formatMoney` and import the canonical one from `@/lib/utils`,
  passing the active `locale` and the display currency.
- Verify: open the Add-transaction sheet in `id`, enter an amount, and confirm the total
  matches the input's grouping and the currency symbol used elsewhere.

### R4-B3 · Fx1 · Minor · `[read]` — the carry-forward amount field silently discards a minus sign

- `apps/web/src/components/tax/loss-carryforward-editor.tsx:81`
  `sanitizeAmount` strips every `-` from the typed value, and the comment explains why: the
  downstream computation clamps a negative carry-forward to 0 with no feedback.
- The user typing `-500` sees the field silently become `500`, with no message explaining
  that a negative carry-forward is meaningless. The behaviour is correct; the silence is not.
- Fix: keep the strip, but show a short inline hint when a sign was removed.
- Verify: type `-500` into the stock-pot field and confirm an explanation appears.

### R4-B4 · Fx2 · Minor · `[read]` — the "Can't reach the API" state carries no diagnostic, and the dev stack's API port can be shadowed

> **Corrected 2026-10-25 (before any fix PR).** The original wording said "the API's own log
> showed nothing (it does not log requests)". That is **wrong**: Fastify's default request
> logging is on — `services/api/src/app.ts:148-199` passes a pino instance, so the API emits
> `incoming request` / `request completed` with the status code. The log was empty during the
> port-shadowing incident **because the requests never arrived** — the emptiness is the
> diagnostic tell, not a missing log. The hazard and the fix are unchanged; the finding is
> that neither the user nor the developer has a way to tell "the API is down" from "the
> request reached a different server".

- `apps/web/src/components/data-state.tsx` renders one message for every non-401/429 failure.
  When the API is genuinely unreachable that is right, but when the request reached a
  _different_ server the message is wrong in a way the user (and the developer) cannot see.
- This is not hypothetical. During this round's first live pass **every** data page rendered
  "Can't reach the API" while the API process was alive and healthy, because a foreign
  service was listening on `127.0.0.1:3000` and the Pocket API binds `*:3000` — the more
  specific loopback bind wins, so the web app's `API_URL=http://localhost:3000` reached the
  wrong server. The API's request log stayed **empty** (the requests never reached it), the
  web log showed nothing useful, and every page degraded to the same undifferentiated card.
- `Makefile`'s `dev` target frees only port 3005 (`fuser -k 3005/tcp`); the API's port is
  never checked.
- Fix: (a) bind the API to `127.0.0.1` in local dev so a loopback-specific squatter cannot
  shadow it, or check the port at startup and fail loudly; (b) keep the API's existing
  request log (it is already on) and make the empty-log case recognisable as "the request
  never arrived" rather than "the API is not logging"; (c) keep the UI copy as is — it is
  correct — but let the API's identity be checkable (a `/health` payload the web app can
  compare against the configured `API_URL`).
- Verify: occupy `127.0.0.1:3000` with another listener, start the web app, and confirm the
  failure is reported as a port conflict at startup rather than as "Can't reach the API" on
  every page.

## Batch C — scope & data correctness in the UI (`fix(web)`)

### R4-C1 · Fx7 · Major · `[read]` — the Activity ledger silently ignores a holder scope

- `apps/web/src/app/[locale]/(app)/transactions/page.tsx:53-54`:
  `const selectedId = await getSelectedPortfolioId(); const aggregate = selectedId === null;`
  and `lib/server-api/_shared.ts:55-57` returns `null` for **both** "no portfolio selected"
  and "a holder is selected" — `scope.kind === "portfolio" ? scope.portfolioId : null`.
- So under a holder scope (`h:<id>`) `aggregate` is true and the page calls
  `loadNetworthTransactionsPaginated(...)` for **all** portfolios. Every other scope-aware
  page resolves the holder correctly through `resolveHolderScope()`
  (`lib/server-api/_shared.ts:203-210`) — `/holdings`, `/insights`, `/income`, `/tax`,
  `/trades`, `/savings`.
- The anomaly badge inherits the same gap: `lib/server-api.ts:94-99`
  (`selected ? loadAnomalies(selected) : loadNetworthAnomalies()`), whose comment claims it
  matches the Activity page — which is the page that is wrong.
- Scenario: the user picks a holder who owns two portfolios. Holdings, Insights and Tax show
  that holder only. Activity shows **every holder's** transactions, and a Portfolio column
  appears. The user reads another holder's trades as their own.
- The scope switcher only offers a holder scope when the holder owns ≥2 portfolios
  (`components/portfolio-switcher.tsx:32-36`), so the exposure is limited to those users —
  but for them it is a data-scoping error, not a cosmetic one.
- Fix: resolve the holder scope on the Activity page the way the other pages do —
  `resolveHolderScope(portfolios)` and pass it to the transaction and anomaly loaders; and
  make `getSelectedPortfolioId` unable to conflate the two `null` cases (return a
  discriminated scope rather than `string | null`).
- Verify: select a holder that owns two portfolios and confirm the Activity ledger, the
  anomaly badge and Holdings list the same transactions.

### R4-C2 · Fx7 · Minor · `[read]` — `/holdings` carries two parallel scope encodings

- `apps/web/src/app/[locale]/(app)/holdings/page.tsx` accepts a `?portfolio=<id>` parameter
  that overrides **only** the positions table (`loadHoldings(costBasis, portfolioParam)`),
  while the hero chart, the allocation donut and the sidebar net worth follow `?scope=`.
  `components/portfolio-switcher.tsx:82-101` writes `?scope=`; nothing labels the other
  parameter's effect on screen.
- Scenario: a link or a bookmark carrying `?portfolio=<id>` opens Holdings showing that
  portfolio's positions next to the scope aggregate's net worth and allocation — two
  different scopes on one screen, with nothing saying so.
- Fix: make `?portfolio=` write `?scope=p:<id>` (the documented encoding) so there is one
  scope parameter, and drop the special case.
- Verify: open `/en/holdings?portfolio=<id>` and confirm the hero, the allocation and the
  positions all follow that portfolio.

## Batch D — accessibility (`fix(web)`)

### R4-D1 · Fx4 · Major · `[read]` — every chart is an unnamed `role="application"`

> **Corrected 2026-10-25 (before any fix PR).** The original wording said the
> `accessibilityLayer` prop "appears nowhere in the codebase" and implied the keyboard
> navigation was missing. Re-reading `recharts@3.10.1` shows the layer is **on by default**
> (`lib/context/accessibilityContext.js` — `useAccessibilityLayer()` returns
> `state.rootProps.accessibilityLayer ?? true`), so the keyboard-driven tooltip
> (`lib/component/Tooltip.js:165`) and a focusable chart surface are already there. The
> **missing** part is the accessible **name**, and the default **role** is wrong. The finding
> is narrower but still real.

- All 9 recharts charts (`components/charts/{allocation-donut,contributions-chart,eps-actual-estimate-chart,forecast-chart,hero-overlay-chart,income-bar-chart,price-chart,revenue-earnings-chart}.tsx`
  and `components/insights/yearly-returns-card.tsx`) render an SVG with no `role="img"`, no
  `aria-label`, and no `<figcaption>`/`sr-only` summary. The only `role="img"` in the app is
  `components/brokerage-icon.tsx:31,61`.
- `recharts@^3.10.1` renders `<title>`/`<desc>` from the chart's `title`/`desc` props
  (`lib/container/Surface.js:47`) and sets the surface's `role` from `otherAttributes.role`,
  falling back to `role="application"` **when the accessibility layer is on**
  (`lib/container/RootSurface.js:47-57`). **No chart passes `title`/`desc`,** and no chart
  overrides the role — so every chart is an unnamed `role="application"`.
- `role="application"` is also the wrong role here: it tells a screen reader to switch into
  application mode (keys pass through to the graphic) for a chart the user wants to _read_.
- Scenario: a screen-reader user reaches the net-worth chart and hears an unlabelled graphic
  with no values; a keyboard user cannot read a single point. The information exists only as
  pixels.
- Fix: give every chart an accessible **name** by passing `title`/`desc` (naming the series
  and the range) and override the surface's role with `role="img"`, so it is announced as a
  graphic rather than as an application. Keep the keyboard-driven tooltip the default-on
  accessibility layer already provides, and pair the name with a text equivalent of the data
  (see R4-E8).
- Verify: with a screen reader, each chart announces its name and series; with the keyboard,
  arrow keys move through the points and their values are announced.

### R4-D2 · Fx5 · Major · `[read]` — route changes never move focus

- `apps/web/src/components/route-transition.tsx:38-40` resets the shell's scroll container on

- Scenario: a keyboard or screen-reader user activates a link, the new page renders, and

  rather than from the new content.
- Fix: after a user-initiated route change settles, move focus to the new page's `<h1>`
  (or `<main>`), and skip that on first paint so it never steals focus on load.
- Verify: tab to a nav link, activate it, and confirm focus lands on the new page's heading.

## Things that looked like bugs but are not

Five signals turned out **not** to be defects, and are recorded here so the next round does
not re-chase them.

1. **"Can't reach the API" on every data page (first live pass).** Not an app defect — a
   **port-shadowing** artefact of this machine: a foreign service was bound to
   `127.0.0.1:3000` while the Pocket API binds `*:3000`, so the web app's
   `API_URL=http://localhost:3000` reached the wrong server (its `/health` answered 200 and
   every other path 404'd with another server's Fastify error shape). Re-running with the API
   on a free port gave a completely clean pass. The underlying hazard is tracked as R4-B4,
   but the pages themselves are fine.
2. **"Unnamed" switches on Settings and Admin (live).** The walkthrough's heuristic only
   considers `aria-label` / `aria-labelledby` / `title` / text content, so it misses
   `<label for>` associations. The switch in question (`#shortcuts-enabled`) does have
   `label[for="shortcuts-enabled"]` = "Keyboard shortcuts". Same for the 7 "unlabelled
   inputs" on `/en/admin` — those are Radix Switch's internal `aria-hidden="true"`
   checkboxes, which are correctly outside the accessibility tree.
3. **Sub-32 px targets in the tables (live).** Most measured "small targets" are table
   header sort links, inline instrument-name links and the `sr-only` skip link (1×1) —
   inline links in a sentence are exempt from WCAG 2.5.8. The genuine ones are R4-D7 (7×7)
   and R4-D8 (16×16). The admin "Drag to reorder" grip measures 16×16 because the
   `touch-target` utility extends its **hit area** via an invisible `::before`, which
   `getBoundingClientRect()` does not see.
4. **Eight console errors on every page (live).** All are
   `GET /api/auth/session → 500 [auth][error] MissingSecret: Please define a 'secret'` — the
   stock `.env.example` leaves `AUTH_SECRET` blank, so Auth.js's session route throws while
   the app's own auth gate correctly stands down and `DEV_AUTH_TOKEN` authenticates the
   rest. This is a **local-dev configuration artefact**, not a defect in a configured
   deployment; it does mean the documented local setup produces a wall of red on every page,
   which is worth a note in the README but is not a product bug.
5. **The `/reports` hub's scope (R4-G4, filed as "no page header and no scope indicator").**
   Not a defect. The hub has the `PageHeader` every top-level page has
   (`app/[locale]/(app)/reports/page.tsx:35`) and the shell's global `PortfolioSwitcher`
   (`components/app-shell.tsx:105`), and its seven cards follow the **selected** scope
   exactly like its neighbours — every loader in `components/reports/reports-data.ts` resolves
   the scope itself (`getSelectedPortfolioId()` → the portfolio endpoint,
   `resolveHolderScope()` → the holder endpoint, neither → the all-portfolio one). The
   finding was filed on a wrong reading, corrected once in the wrong direction, and is
   closed as **not reproducible**; the scope line the fix PR had shipped on the strength of
   that wrong reading was removed again in the same PR. The full evidence is in R4-G4.
